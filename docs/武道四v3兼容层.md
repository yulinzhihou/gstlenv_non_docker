# 武道四 v3 Server1 崩溃分析与兼容层

> 关联报告: `运行报告-武道四v3服务端VM验证.md`（主目录）
> 缓解工具: `tools/fwlog.c`

## 一、现象

武道四 v3 服务端（tlbb.tar.gz）中 **Server1（场景服）** 在 64 位 EL9 环境启动后约 0.3~3 秒确定性 SIGSEGV，崩点位于 Manager 初始化链中后段（FashionAuctionManager / HumanLevelManager / TopList_Server 附近随机）。

## 二、根因（gdb 17.2 精确定位）

```
#0  fwrite() from /lib64/libc.so.6
#1  0x000000000072fc0e in ?? ()        ← Server1 偏移 0x72fc0e
#2  0x3d3d3d3d3d3d3d3d ...             ← 栈被 '='（日志分隔线）整段覆盖
rcx = 0                                 ← fwrite 第4参数 FILE* = NULL
```

**机制**：Server1 日志格式化函数将 `==================` 分隔线（60 字节）写入约 56 字节固定栈缓冲，**溢出约 4 字节**，覆盖相邻栈帧中的 FILE* 指针 → 后续 `fwrite(ptr, 1, 56, NULL)` → 内部解引用 NULL → SIGSEGV。

此缺陷由端编译期栈缓冲大小错误导致（或 32 位指针宽度残留），与安装器配置、数据库、库依赖、内存资源均无关。

## 三、兼容层（tools/fwlog.c）

拦截 `fwrite`：当 `stream == NULL` 时直接返回 0（丢弃日志，不崩溃）。

```bash
# 编译（需 gcc）
gcc -shared -fPIC -O0 -o fwlog.so fwlog.c -ldl

# 使用
cd /home/tlbb/tlbb1/Server
export LD_LIBRARY_PATH=/home/tlbb/tlbb1/Server
export LD_PRELOAD=/path/to/fwlog.so
export LC_ALL=C
./Server1
```

**效果**：可将 Server1 初始化推进 20+ Manager（CityVisitorManager / StatusRuler / ItemManager / DaemonThread 等全部 OK），但最终仍在 TopList_Server 后崩溃——**部分缓解，非根治**。

## 四、端作者修复方向

1. 将日志分隔线写入缓冲改为动态分配或 `vsnprintf`（带长度上限）；
2. 检查所有固定栈缓冲（`char buf[56]` 类）与写入长度；
3. 检查 64 位环境下 FILE* / 指针存储宽度（疑似 32 位截断残留）。

## 五、诊断环境（VM 上已就绪）

```bash
# el9 版 gdb（正确解析 el9 core / 运行 el9 目标）
dnf --installroot=/opt/el9 install -y gdb

# 回溯 core
chroot /opt/el9 /usr/bin/gdb -batch \
  -ex "set pagination off" -ex "set debuginfod enabled off" \
  -ex "bt 25" /home/tlbb/tlbb1/Server/Server1 /tmp/core.Server.*

# ODBC 跟踪（诊断用，用完必须关！默认 Trace=No）
# /etc/odbcinst.ini 中 Trace=Yes 会膨胀至数 GB 填满磁盘
```

## 六、注意

- **ODBC trace 必须默认关闭**（Trace=No），调试后立即清理 `/tmp/odbc_trace.log`；
- **Server 进程启动加 `ulimit -c 0`** 防止崩溃 core（2.1GB/次）填满磁盘。
