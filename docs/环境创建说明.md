# 环境创建说明（从零到开服）

> 目标：在一台全新的 Linux 服务器上，从安装环境到跑起《天龙八部》服务端。
> 命令体系与 gstlenv 完全一致（gs 原命令名），帮助入口：`gs`，统一入口：`gsctl <命令> [参数...]`。

---

## 阶段一：安装运行环境（约 5~15 分钟）

```bash
# 1. 上传 src 目录到服务器
#    例: scp -r src root@服务器IP:/root/

# 2. 进入并安装
cd /root/src
bash install.sh
```

安装完成标志：看到「TLBB 原生环境安装完成」横幅，且 `gs` 命令可用。

---

## 阶段二：准备服务端文件

### 2.1 获取服务端压缩包

- 格式：`tlbb.tar.gz` 或 `tlbb.zip`
- 默认上传位置：**/root 目录**；其他位置可显式执行 `untar /绝对路径/压缩包.tar.gz`。

```bash
# 例: 上传后确认
ls -l /root/tlbb.tar.gz
```

### 2.2 解压服务端

```bash
untar
# 成功时明确输出: 服务端目录 /tlgame/tlbb, 配置目录 /tlgame/tlbb/Server/Config
# 以 /root/.gs/.env 的 TLBB_PATH 为准; 首次部署不需要已有旧端
# 换端前备份到 BACKUP_DIR/tlbb-before-untar-时间戳-随机标识.tar.gz
```

支持 `tlbb/Server/`、直接的 `Server/` 以及额外嵌套目录；包中必须有且仅有一套
`Server/Config`，并包含 `ServerInfo.ini`、`LoginInfo.ini`、`ShareMemInfo.ini`。
先在临时目录解压并检查，再替换目标目录。原包、解压或旧端备份失败时，不显示成功。
成功后原包保留为同目录下的 `时间戳-随机标识-原包名`；包内服务端之外的附属文件保留到
目标旁的 `tlbb.archive-extra-*` 目录，并打印位置，不会静默丢弃。

旧版 `untar` 误报成功时的排查与更新方法见 [解压修复说明](untar-repair-20261104.md)。

---

## 阶段三：配置服务端

### 3.1 写入数据库配置

```bash
setini
```

自动将数据库 IP/端口/账号/密码写入服务端 `config/ServerInfo.ini`、`LoginInfo.ini`、`ShareMemInfo.ini`，
并生成 `/etc/odbc.ini` 与 Billing 的 `/tlgame/billing/config.yaml`。
写配置前先备份并规范 `run.sh` 的旧 `/home/tlbb`、`/home/billing` 路径，
检查 `cd` 目录、实际可执行文件及 `LD_PRELOAD` 依赖；缺失时停止并要求修复 `run.sh`，
不继续写 INI/ODBC/Billing 配置。本机 Billing 启动命令已存在则不重复添加。

### 3.2 检查配置（可选）

```bash
cat /tlgame/tlbb/Server/Config/ServerInfo.ini   # 服务端实际配置文件
curgs                                            # 查看环境总配置
```

## 阶段四：启动开服

```bash
# 1. 开启服务端
runtlbb

# 2. 实时监控 run.sh 中的启动进程（q 或 Ctrl+C 退出）
runtop
# 单次输出，便于复制排查；也支持 runtop --interval 1 调整刷新秒数
runtop --once

# 3. 查看日志（确认无报错）
gslog
```

`runtop` 默认每 2 秒刷新，只显示当前 `TLBB_PATH/run.sh` 的直接启动项，不再混入
MySQL 或其他服务端目录中的同名进程。支持常见的 `cd`、引号路径、简单路径变量、
`nohup`、`nice`、后台启动、`shm start`（显示为 ShareMemory）和 billing 启动命令。
停止的启动项仍显示 `STOP`，文件缺失或不可执行显示 `MISSING`；同一启动项的多个 PID
逐行列出。CPU 为采样区间占用率（单核 100%，多线程可能超过 100%），RSS 为实际驻留内存。
非交互终端、管道及重定向自动输出单次快照，附带各启动项的完整路径，不持续占用会话。

监控仅静态读取脚本，不执行或递归运行其中的命令；不展开命令替换，不支持动态生成的
路径、嵌套启动脚本或复杂函数控制流。遇到无法解析的语法会提示，条件分支内的静态条目
也不代表该分支已执行。修改 `run.sh` 后重新进入 `runtop` 以重新加载启动清单。

**开服确认**：进程处于 `RUN` 不等于游戏已就绪。还需结合 `gslog` 检查日志，
用 `ss -ltnp` 检查配置中的登录、游戏和 billing 端口，并进行客户端实际登录测试。

### 分步调试

```bash
step --list
step --check
# 典型五程序清单，以 --list 的实际编号为准：
step 1  # Billing
step 2  # shm / ShareMemory
step 3  # Login
step 4  # World
step 5  # Server（也可能是 Server1、Server_fix）
```

每次只运行所选程序，保留原命令的参数、环境、`setarch`/`env` 包装；
不执行原脚本中的清理、延时或内核写入。游戏程序在前台运行时需另开 SSH 会话继续下一步，
不要用 Ctrl+C 退出后再误以为进程仍在运行。`billing up -d` 本身可能转入后台，
以 Billing 日志和 `runtop` 为准。已有相同路径的程序运行时拒绝重复启动，不自动关服。
额外 Server 实例或其他程序生成独立编号；W机验证模式不含本机 Billing，编号随之变化。
详细迁移、备份、解析限制见 [启动路径与 step 命令](startup-steps-20261104.md)。

## 阶段五：客户端连接

1. 修改客户端 `ServerList.txt` 服务器 IP 为本机公网 IP；
2. 安全组 / 防火墙放行：`3306 / 13580 / 15680 / 21818 / 51888 / 61888`（默认值对齐 gstlenv）；
3. 客户端登录测试。

## 日常运维速查

| 操作 | 命令 |
|---|---|
| 命令帮助 | `gs`（菜单）/ `gsctl <命令> [参数...]`（统一入口） |
| 关服 | `close` |
| 重启 | `restart` |
| 备份数据库+版本 | `backup`（0=全部 1=版本 2=数据库，存 /tlgame/backup/） |
| 还原数据库 | `restore web 备份文件绝对路径` / `restore tlbbdb 备份文件绝对路径` |
| 删档重导 | `reset`（会清空玩家数据！先 backup） |
| 封号 / 解封 | `setvalid 账号 1` / `setvalid 账号` |
| 充值点数 | `setpoint point 5000 账号`（类型: point/yuanbao/zengdian/menpaipoint/guildpoint/points/vmoney） |
| 增加虚拟内存 | `swap 4`（4GB） |
| 换端 | 上传新包到 /root 后 `change` |
| 清理日志 | `rmlog` |
| 备份日志 | `logbak`（`logbak cron 1 10` 定时） |
| 删除旧备份 | `delbak 5`（保留 5 份） |
| 重构环境 | `rebuild` |
| 卸载 | `remove` |
